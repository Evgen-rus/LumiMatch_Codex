# AGENTS.md — LumiMatch

Локальный Codex-workflow: PDF дизайн-проекта → требования → каталог разрешённых поставщиков → визуальная проверка → HTML/Markdown/JSON-подборка. Codex сам выполняет AI/vision-работу.

## Контекст и источники истины

1. Прочитай этот файл, затем карту в [README.md](README.md).
2. Открой только раздел [ARCHITECTURE.md](ARCHITECTURE.md), относящийся к изменяемой стадии, и нужный документ из карты.
3. Проверь реальные входы/артефакты стадии, затем нужные исходники и callers через `rg`. Не читай целиком большие директории, каталоги, логи или чужую историю.

`lumimatch/` — production; `tests/` — проверки; `experiments/visual_retrieval/` — изолированный эксперимент; `samples/` — входы; `data/` — контракты/кэш; `output/` — результаты; `docs/` — инструкции и evidence.
Код и тесты показывают фактическое поведение; архитектура задаёт контракт; отчёты фиксируют конкретный прогон. Расхождение явно зафиксируй, не ослабляй gate ради согласования текста.

## Основные команды

PowerShell, из корня проекта; Python 3.12+, зависимости только в локальной `.venv`:

```powershell
.\setup.ps1
.\.venv\Scripts\python.exe -m lumimatch --help
.\.venv\Scripts\python.exe -m pytest tests/test_scoring.py -q
```

Setup нужен только при подготовке окружения. Другие команды, выбор проверок и побочные эффекты — [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Критические ограничения

- Только `suppliers.txt`; HTTP-first, ограниченный обход, retry/rate limits, без обхода CAPTCHA, авторизации и защит. Сбой поставщика не останавливает остальных.
- Не добавляй внешний LLM/vision runtime, OpenAI SDK, API-ключ, SaaS или тяжёлый frontend без отдельного запроса. Не меняй глобальные Python, PATH, Git и системные настройки. Зависимости обновляй в `requirements.txt`.
- Не выдумывай свойства, SKU, ссылки, цены и наличие. Сохраняй файл, страницу, тип источника и confidence. Размеры изделия — в mm; упаковка и фото соседних SKU не подходят.
- Hard gates, широкий visual pool, явный reject и live recheck без кэша обязательны. Основной отчёт — только `in_stock`; unavailable-диагностика — только четыре временных статуса из архитектуры. `unknown` глобально запрещён; supplier capability не отменяет customer-facing gate.
- Не выбирать top-5 до Codex visual review. Другой цвет — только `color_alternative` после отсутствия хорошего основного варианта. Не доказывай exact match одним score.
- Golden targets не управляют production inventory/hydration. Перенос экспериментов в production требует отдельного подтверждённого решения. Кэш и raw evidence сохраняй.

## Orchestration и model routing — единственный раздел выбора моделей

| Роль | Модель / reasoning | Работа |
|---|---|---|
| Lead по умолчанию | Astra `gpt-6-astra`, Low | Понимание, архитектура, минимальный контекст, декомпозиция, интеграция, конфликты и принятие результата; маленькие задачи самостоятельно |
| Worker | Luna `gpt-5.6-luna`, Low | Scouting, usages, логи, факты, документация, локальные рутинные правки и простые проверки |
| Сложный worker | Luna `gpt-5.6-luna`, Max | Основная нетривиальная реализация, bounded-компонент, глубокий анализ модуля, локальный debugging/рефакторинг; не тривиальные задачи |

Это политика проекта, а не автоматически применённая конфигурация Codex. Выбирай параметры доступным инструментом; не заявляй смену модели/reasoning, если она не выполнена. Если переключение текущего lead недоступно, сообщи ограничение; не создавай второго lead ради переключения.

Только текущий lead повышается до Medium при сложной архитектуре, изменении нескольких систем, тяжёлом debugging, важной миграции, высоком риске регрессии, конфликтующих результатах или ненадёжной попытке на Low. Сначала Low → Medium; High/Max для lead — только с крайне веской явно названной причиной. Дополнительные Astra-субагенты по умолчанию запрещены: текущий lead + workers предпочтительнее.

Лимиты на всё дерево: один lead, обычно до двух workers одновременно, из них максимум один Max. Для большой задачи допустимы три независимых workers, только если это экономит общее время/контекст и позволяет runtime. Workers самостоятельно не размножаются; делегирование согласует lead.

Маленькая задача — lead сам; средняя — один worker; большая — два, при обосновании три; архитектурное решение остаётся у lead. Не делегируй, если handoff дороже самой работы, и не дублируй исследование одной области. Большую безопасно отделимую реализацию/чтение передавай worker.

Перед запуском кратко определи: зачем worker, почему выгоднее lead, минимальную модель, границы файлов и ожидаемый результат. Передавай fresh context (`fork_turns="none"`, если доступен): цель, файлы, ограничения, результат, проверки; не весь родительский диалог. Назначай непересекающиеся области записи; общие контракты интегрирует lead. Не отменяй чужие изменения.

Handoff: `FINDINGS / CHANGES / FILES / RISKS / VERIFICATION` — короткие факты, пути, команды и результаты; без эссе и chain-of-thought. Lead проверяет diff и стыки, не перечитывает весь исследованный worker контекст.

## Завершение и verification

После необходимого изучения сразу реализуй; вопрос нужен только при блокирующей неопределённости. Не заканчивай планом/scaffold. Используй существующие решения и минимум файлов.
Сначала проверки изменённой области по [DEVELOPMENT.md](docs/DEVELOPMENT.md); расширяй их при риске общих контрактов, сбое или новой правке. Не повторяй дорогой полный набор без причины.
Перед завершением проверь итоговый diff, интеграцию, UTF-8 и архитектурные ограничения. Меняешь контракт/pipeline — обнови архитектуру. Для runtime-изменений выполни релевантный реальный sample run и сохрани результат/ограничения в `docs/SAMPLE_RUN.md` и `output/`; для документации достаточно ссылок, команд и diff без сетевого пересбора.
