# AGENTS.md — LumiMatch Codex

## Назначение проекта

LumiMatch помогает продавцу светотехники быстро подбирать конкретную модель или максимально близкий аналог по дизайн-проекту.

Типичный вход:
- PDF с техническими планами;
- PDF с интерьерными визуализациями;
- иногда есть подписи и размеры;
- очень часто точных характеристик нет, а светильник задан только визуально.

Типичный объём: примерно один проект в неделю, до 20 позиций на подбор.

Искать товары можно только у поставщиков из `suppliers.txt`.

## Ключевой принцип: Codex — сам AI-оператор

Проект работает через Codex.

Не создавай внешний LLM/vision runtime без отдельного запроса пользователя.
Не требуй `OPENAI_API_KEY`.
Не добавляй OpenAI SDK только ради распознавания PDF, изображений или сравнения светильников.
Не проектируй SaaS и не строй отдельную AI-службу.


## Python-окружение и зависимости

Проект Python-first. Рабочее окружение должно быть изолировано внутри этой папки.

Правила:
- используй Python 3.12+;
- все Python-зависимости устанавливай только в локальное `.venv` этого проекта;
- если `.venv` ещё нет, сначала запусти `setup.ps1` либо создай эквивалентное окружение самостоятельно;
- не используй глобальный `pip` и не устанавливай пакеты глобально;
- основной список Python-зависимостей — `requirements.txt`;
- если добавляешь или удаляешь библиотеку, сразу обновляй `requirements.txt`;
- Python-команды на Windows запускай через `.\\.venv\\Scripts\\python.exe`;
- для Playwright используй браузер, установленный командой `.\\.venv\\Scripts\\python.exe -m playwright install chromium`;
- не меняй глобальный Python, PATH, системные настройки или глобальную конфигурацию Git;
- не добавляй OpenAI SDK и не требуй API-ключ для AI/vision-задач: их выполняет сам Codex.

Если отдельная библиотека действительно не нужна для MVP, не добавляй её заранее.


Используй собственные мультимодальные возможности Codex для:
- чтения PDF и изображений;
- понимания визуализаций;
- выделения светильников;
- сопоставления референса и кандидатов;
- оценки сходства;
- принятия инженерных решений во время выполнения задачи.

Код и локальные инструменты нужны прежде всего для автоматизации рутинной части: обход сайтов, извлечение карточек, скачивание изображений, хранение каталога, фильтрация, кэширование и формирование результата.

## Референсный репозиторий

Изучи как архитектурный референс:
https://github.com/Evgen-rus/Contact_harvester

Не изменяй Contact_harvester и не превращай эту задачу в его модуль.

Полезные идеи, которые можно адаптировать:
- HTTP-first;
- browser fallback только при необходимости;
- разделение collector / extractor / normalization / service;
- ограниченный обход;
- retry;
- Playwright для публично отрисованных страниц;
- ошибка одного домена не ломает весь запуск;
- структурированные модели;
- тестируемость;
- не обходить CAPTCHA и авторизацию.

Не копируй телефонную логику.

## Общий workflow

Целевой поток:

`сайты поставщиков -> локальный каталог -> дизайн-проект -> FixtureRequirement -> shortlist кандидатов -> визуальная проверка Codex -> итоговая подборка`

Не обходи все сайты заново для каждой позиции, если можно использовать локальный каталог и кэш.

## Сначала изучить реальные входные данные

В `samples/` уже лежат два реальных PDF:
- `Dan_dia-2.pdf` — техническая часть;
- `Dan_vis.pdf` — интерьерные визуализации.

Используй их как основной end-to-end тест.

Не выдумывай характеристики, которых нет в проекте.
Для каждого извлечённого требования сохраняй источник: файл, страницу, тип источника и уверенность.

## Сущность FixtureRequirement

Сделай простую структурированную модель, примерно:
- id;
- room;
- fixture_type;
- quantity;
- visual_description;
- color;
- shape;
- mounting;
- approximate_dimensions;
- exact_dimensions;
- technical_constraints;
- source_pages;
- confidence;
- reference_images/pages.

Неизвестное оставляй неизвестным.

## Аудит поставщиков

Перед основной реализацией быстро проверь все сайты из `suppliers.txt` и создай `docs/SUPPLIER_AUDIT.md`.

Для каждого сайта проверь:
- robots.txt;
- sitemap/sitemap index;
- доступность карточек обычным HTTP;
- JSON-LD / schema.org Product;
- OpenGraph/meta;
- пагинацию;
- категории;
- артикул;
- название;
- цену;
- наличие;
- характеристики;
- размеры;
- фотографии;
- canonical URL;
- JavaScript-зависимость;
- нужен ли Playwright;
- есть ли публичный XHR/API, который рационально использовать.

Аудит не должен превращаться в многодневное исследование и не должен останавливать MVP.

## Сбор сайтов

Порядок предпочтений:
1. sitemap;
2. обычный HTTP;
3. JSON-LD / структурированные данные;
4. HTML;
5. лёгкий site-specific adapter;
6. Playwright только когда иначе нельзя получить публичный контент.

Не обходи CAPTCHA, авторизацию и технические защиты.
Добавь rate limit, retry, page limits и защиту от циклов.
Ошибка одного поставщика не должна ломать остальных.

## Поиск кандидатов

Не пытайся визуально сравнить референс со всем каталогом.

Сначала сделай дешёвый shortlist по структурированным данным:
- категория;
- тип монтажа;
- цвет;
- форма;
- размеры;
- технические характеристики;
- название/описание;
- lexical/full-text similarity.

SQLite FTS допустим и предпочтителен тяжёлой инфраструктуре.

После этого скачай/подготовь изображения top-N кандидатов и используй собственное визуальное понимание Codex для финальной оценки.

Оцени раздельно:
- visual_similarity;
- type_match;
- dimension_match;
- technical_match;
- overall_score.

Hard constraints важнее визуального сходства.

Классы результата:
- вероятное точное совпадение;
- очень близкий аналог;
- похожий вариант.

Не называй точным совпадением то, что не доказано.

## Итог по каждой позиции

Обязательно показать:
- референс/страницу из проекта;
- что распознано;
- помещение/контекст;
- 3–5 лучших кандидатов, если они есть;
- настоящее фото товара;
- прямую ссылку на карточку;
- поставщика;
- название;
- артикул;
- цену, если публична;
- наличие, если публично;
- размеры/важные характеристики;
- класс совпадения;
- короткое объяснение сходства и отличий.

Не придумывай товар, URL, артикул, цену, наличие или характеристики.

## UX

На первом этапе не нужен тяжёлый отдельный frontend.

Приоритет — Codex workflow + удобный HTML/Markdown-отчёт и локальные данные.
Если лёгкий локальный UI действительно сокращает работу и получается без лишней архитектуры, допустим Streamlit, но это не обязательное условие первого прохода.

Главное: человек кладёт новый проект в папку, запускает Codex-задачу и получает понятную подборку.

## Кэш

Не повторяй дорогую работу без необходимости.
Кэшируй:
- каталоги;
- скачанные изображения;
- обработанные PDF;
- FixtureRequirement;
- shortlist;
- предыдущие результаты.

## Разработка

Перед изменениями:
1. прочитай `AGENTS.md`, `TASK.md`, `WORKFLOW.md`;
2. изучи sample PDF;
3. изучи Contact_harvester;
4. проверь реальные сайты;
5. коротко зафиксируй архитектуру.

После этого сразу реализуй.

Не заканчивай задачу только планом или scaffold.
Работай автономно до максимально рабочего результата.
Вопрос задавай только если без ответа невозможно продолжать.

Избегай overengineering.

Если отдельный поставщик создаёт проблемы, зафиксируй ограничение и продолжай с остальными.
Приоритет — рабочий end-to-end на реальном sample, а не идеальная поддержка всех сайтов.

После изменений:
- запусти тесты;
- проверь критичную логику;
- сделай реальный sample run;
- исправь очевидные проблемы;
- сохрани результат в `docs/SAMPLE_RUN.md` и `output/`.
