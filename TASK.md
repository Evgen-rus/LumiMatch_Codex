# TASK.md — первая реализация LumiMatch

## Цель

Сделать рабочий MVP помощника, который по реальному дизайн-проекту находит у заданных поставщиков конкретную модель светильника либо максимально близкие аналоги и выдаёт результат с фотографиями и прямыми ссылками.

Работай через собственные мультимодальные возможности Codex. Никакой внешний OpenAI API для AI-части не нужен.

## Исходные данные

Реальные файлы уже находятся в `samples/`:
- `Dan_dia-2.pdf`;
- `Dan_vis.pdf`.

Список поставщиков — `suppliers.txt`.

Архитектурный reference:
https://github.com/Evgen-rus/Contact_harvester

## Что нужно сделать

### Этап 1. Изучить sample

Разбери оба PDF.

Определи:
- какие типы светильников встречаются;
- где есть технические подписи;
- где есть только визуальные референсы;
- какие позиции можно связать между планом и визуализациями;
- какие параметры известны достоверно, а какие только предполагаются.

Сохрани первичную структуру требований в `data/fixture_requirements.json` или SQLite.

### Этап 2. Аудит поставщиков

Проверь сайты из `suppliers.txt` и создай `docs/SUPPLIER_AUDIT.md`.

Найди наиболее устойчивый и простой способ извлекать товарные карточки.
Не строй 15 сложных парсеров, если generic extractor покрывает значительную часть сайтов.

Для первого реально работающего end-to-end выбери несколько наиболее удобных поставщиков, затем расширяй покрытие.

### Этап 3. Локальный каталог

Сделай обновляемый локальный каталог товаров.

Обязательные данные для результата:
- supplier;
- name;
- sku;
- source_url;
- primary_image_url;
- локальная копия изображения или надёжный путь к нему;
- характеристики, которые удалось получить.

Желательные:
- price;
- availability;
- dimensions;
- color;
- material;
- mounting_type;
- wattage;
- color_temperature;
- category/collection.

Добавь дедупликацию и кэш.

### Этап 4. Shortlist

Для каждой `FixtureRequirement` делай первичный shortlist алгоритмически, без AI API.

Учитывай:
- тип;
- монтаж;
- форму;
- цвет;
- размеры;
- технические ограничения;
- текст карточки.

Не нужно сразу идеально ранжировать. Важно сократить каталог до разумного top-N.

### Этап 5. Визуальная проверка самим Codex

Подготовь top-N кандидатов так, чтобы Codex мог быстро посмотреть изображения кандидатов и сравнить их с нужной позицией из sample.

Для каждого кандидата оцени:
- visual_similarity;
- type_match;
- dimension_match;
- technical_match;
- overall_score.

Сохрани объяснение решения.

### Этап 6. Итоговый результат

Сформируй удобный отчёт в `output/`.
Предпочтительно HTML + Markdown/JSON как машинный источник.

По каждой позиции должны быть:
- референс;
- распознанное требование;
- 3–5 кандидатов;
- фото каждого кандидата;
- поставщик;
- название;
- артикул;
- прямая ссылка;
- цена/наличие, если доступны;
- основные параметры;
- класс совпадения;
- почему подходит;
- чем отличается.

Ссылки должны быть реальными и проверенными.

### Этап 7. Проверка на sample

Запусти весь workflow на `samples/Dan_dia-2.pdf` + `samples/Dan_vis.pdf`.

Создай `docs/SAMPLE_RUN.md`:
- какие позиции удалось распознать;
- сколько кандидатов найдено;
- какие поставщики реально поддержаны;
- реальные ссылки на несколько результатов;
- где уверенность высокая;
- где нужна ручная проверка;
- что пока не получилось.

## Acceptance criteria

MVP успешен, если:

1. sample PDF реально разобраны;
2. создано несколько `FixtureRequirement`;
3. собираются настоящие товары минимум с нескольких разрешённых сайтов;
4. каждый выдаваемый кандидат имеет реальное фото и прямую ссылку;
5. артикул соответствует карточке;
6. есть минимум несколько хороших визуально похожих результатов на реальных позициях sample;
7. один сломанный поставщик не останавливает запуск;
8. повторный запуск использует кэш;
9. нет выдуманных товаров/URL/характеристик;
10. есть понятная инструкция для следующего реального проекта.

## Ограничения

Не добавляй внешний OpenAI API.
Не требуй `OPENAI_API_KEY`.
Не делай микросервисы, Kubernetes, Elasticsearch, отдельную vector DB и тяжёлый frontend без необходимости.
Не пытайся идеально автоматизировать то, что Codex в текущей сессии может надёжно проверить сам.

## Режим работы

Работай автономно до максимально рабочего результата.
Не заканчивай на исследовании или плане.
Если отдельный сайт мешает — зафиксируй проблему и иди дальше.
Приоритет — доказать ценность end-to-end на реальном проекте.
